1  Projects: the unit of work in R

“If the first line of your script is setwd(), I will come to your computer and set it on fire.” A light-hearted paraphrase of Jenny Bryan (Bryan 2017)

Lesson goals

By the end of this lesson you will be able to:

  1. Explain why, in the lab, all R work happens inside a project rather than in loose scripts.
  2. Create an RStudio project from the menu and from code, with the QGSL Lab’s standard folder structure.
  3. Tell absolute paths from relative paths and understand the role of the working directory.
  4. Read a data file reproducibly with the here package.
  5. Diagnose the most common beginner error: cannot open file ... No such file or directory.
  6. Configure RStudio to always start with a clean session.

1.1 Setting up your environment

1.1.1 What needs to be installed

We will use four tools throughout the course. Each plays a different role:

Tool Role Where to get it
R The language and the interpreter that runs the code https://cran.r-project.org
RStudio The integrated development environment (IDE): editor, console, file and project manager https://posit.co/download/rstudio-desktop/
Quarto The publishing system that turns text + code into reports, books and websites (this book is built with Quarto) Ships with RStudio; also at https://quarto.org
Git Version control, which records the history of every file in the project https://git-scm.com

An important distinction: R and RStudio are not the same thing. R is the engine; RStudio is the dashboard. You can use R without RStudio (from the terminal or other editors such as VS Code or Positron), but you cannot use RStudio without R.

To check what is installed, run in the console:

R.version.string            # R version
RStudio.Version()$version   # RStudio version (only works inside RStudio)
quarto::quarto_version()    # Quarto version
system("git --version")     # Git version
R.version.string
#> [1] "R version 4.6.1 (2026-06-24)"
WarningKeep R up to date

New packages often require recent versions of R. A rule of thumb for the lab: update R at least once a year, shortly after the x.y.0 release (usually in April), and reinstall your packages afterwards.

1.1.2 A tour of RStudio

When you open RStudio you will see four panes:

  1. Editor (top left): where you write and save scripts (.R) and Quarto documents (.qmd). This is where the real work happens.
  2. Console (bottom left): where R runs commands. Great for quick tests, terrible for keeping work, because nothing you type there is saved in an organised way.
  3. Environment / History / Git (top right): shows the objects in the session’s memory, the command history and, once we enable Git, the state of the files.
  4. Files / Plots / Packages / Help / Viewer (bottom right): file browser, plots, installed packages and documentation.

Two shortcuts you will use hundreds of times per lesson:

Shortcut What it does
Ctrl + Enter (Cmd + Enter on a Mac) Runs the current line (or selection) of the editor in the console
Ctrl + Shift + F10 Restarts the R session (we will see why this matters)

1.2 The problem: loose scripts

Imagine a lab colleague sends you this script to analyse a maize trial:

rm(list = ls())
setwd("C:/Users/joao/Desktop/phd/analyses/maize_2025")

data <- read.csv("ensaio_milho_piloto.csv")
mean(data$produtividade_t_ha)

This script looks harmless, but it has two serious problems:

  1. setwd() with an absolute path. The path C:/Users/joao/Desktop/... only exists on João’s computer. On your computer, on the lab server, or on João’s own computer two years from now (after a reinstall), the script fails on its second line.
  2. rm(list = ls()) gives a false sense of cleanliness. That line deletes the objects in the Environment, but it does not unload packages, does not restore options changed with options() and does not undo changes to environment variables. The script may work in your “dirty” session and fail in someone else’s.

1.2.1 The working directory

To understand the first problem we need one concept: the working directory. It is the folder from which R interprets every relative path. You can query it with getwd():

getwd()
#> [1] "/home/ana/projects/R_Course"

When you write read.csv("ensaio_milho_piloto.csv"), R looks for the file inside the working directory. If the file is somewhere else, R cannot find it. setwd() changes the working directory, which is why it looks like the solution. But it ties the script to one specific machine.

The right question is not “how do I make R find my folder?” but “how do I make sure that anyone, on any computer, can run my code without editing anything?”. The answer is the project.

1.3 The solution: RStudio projects

An RStudio project is a folder containing a .Rproj file. When you open that file (double-click it, or use File > Open Project), RStudio:

  • starts a fresh R session;
  • sets the working directory to the project folder, automatically;
  • keeps history, open tabs and settings separate for each project.

As a result, every path in the code can be written relative to the project root, and the same code works on any computer that has a copy of the folder.

ImportantLab rule

At the QGSL Lab, every analysis lives inside a project. A research question, a paper, a thesis or a course: each one is a project, with its own folder, its own .Rproj and its own Git repository. Loose scripts on the desktop are not accepted in code reviews.

1.3.1 Creating a project from the menu

  1. File > New Project…
  2. Choose New Directory > New Project.
  3. Give it a name with no spaces and no accents (for example maize_trial_2025) and choose where the folder will be created.
  4. Tick Create a git repository (we will use it from lesson 9 onwards).
  5. Click Create Project.

RStudio restarts inside the new project. Notice that the project name appears in the top-right corner of the window.

1.3.2 Creating a project from code: the usethis package

NotePackage intent: usethis

Problem it solves. Project setup tasks (creating the structure, enabling Git, configuring GitHub, adding a licence, creating standard files) are repetitive and easy to get wrong by hand.

Philosophy. usethis automates these tasks with self-explanatory function names (use_git(), use_readme_md(), create_project()), always telling you what it did and what you still need to do. It belongs to the development toolchain maintained by the tidyverse team (together with devtools, roxygen2 and testthat).

Why this one and not the alternatives. The alternative is clicking through RStudio menus or creating folders and files by hand. The menu works fine for one project; usethis wins when we want to standardise dozens of lab projects and record the setup as code, which is reproducible by definition. We will return to it in lesson 9 (Git and GitHub) and in the appendix on building the lab package.

The function usethis::create_project() creates the folder, the .Rproj file and a basic .gitignore, and then opens the new project in RStudio. We will use it to create the project for the maize pilot trial. The rest of this lesson is done from inside that project, exactly as you will work on your own analyses.

1.4 Hands on: the maize trial project

1.4.1 Step 1: create the project inside Documents

We will create the maize_trial_2025 project inside your Documents folder. That folder’s path changes from one operating system to another:

System Documents folder
macOS ~/Documents (that is, /Users/your_user/Documents)
Linux Ubuntu ~/Documents, or ~/Documentos if the system was installed in Portuguese
Windows C:/Users/your_user/Documents

In the RStudio console, run only the line for your system:

usethis::create_project("~/Documents/maize_trial_2025")                     # macOS and Linux
usethis::create_project("C:/Users/your_user/Documents/maize_trial_2025")    # Windows (replace your_user)

If you prefer, let R work out where your Documents folder is. Sys.info()[["sysname"]] returns "Darwin" on macOS, "Linux" on Linux and "Windows" on Windows; on Linux, the xdg-user-dir command reports the folder name in the system’s language:

documents_dir <- switch(
  Sys.info()[["sysname"]],
  Darwin  = "~/Documents",
  Linux   = system("xdg-user-dir DOCUMENTS", intern = TRUE),
  Windows = file.path(Sys.getenv("USERPROFILE"), "Documents")
)

usethis::create_project(file.path(documents_dir, "maize_trial_2025"))

RStudio opens a new session, already inside the project: the name maize_trial_2025 appears in the top-right corner and the Files pane shows the project folder. Any objects you had created stayed in the previous session; from now on, all code in this lesson must be typed in this new session. Check:

getwd()
#> [1] "/home/ana/Documents/maize_trial_2025"
fs::dir_tree(all = TRUE)
#> .
#> ├── .gitignore
#> ├── R
#> └── maize_trial_2025.Rproj

Notice three details:

  • maize_trial_2025.Rproj is the file that marks the folder as a project. Next time, just double-click it to get back to the project.
  • .gitignore lists files Git should ignore (for example .Rhistory and .RData).
  • The R/ folder is created by default; in the lab it holds reusable functions, while analyses go in scripts/.

The :: operator (as in usethis::create_project) calls a function from a package without loading the whole package with library(). We will use this form whenever a package function appears only once, because it makes explicit where the function comes from.

1.4.2 Step 2: the lab’s folder structure

Every QGSL Lab analysis follows the same structure. Still in the new project’s console, create the folders:

folders <- c(
  "data/raw",        # raw data, exactly as they came from the field or the lab
  "data/processed",  # clean data, produced by the scripts
  "scripts",         # analyses, numbered in the order they run
  "R",               # reusable functions
  "output/figures",  # generated plots
  "output/tables",   # generated tables
  "reports"          # Quarto reports
)

fs::dir_create(folders)
fs::dir_tree()
#> .
#> ├── R
#> ├── data
#> │   ├── processed
#> │   └── raw
#> ├── maize_trial_2025.Rproj
#> ├── output
#> │   ├── figures
#> │   └── tables
#> ├── reports
#> └── scripts

Notice that the paths are relative: fs::dir_create("data/raw") creates the folder inside the working directory, which is the project root. This course’s own repository follows the same structure, with a chapters/ folder instead of reports/.

Three rules give this structure its meaning:

  1. Raw data are read-only. Never edit a file in data/raw/ by hand, not even in Excel. Every correction is made in code, which writes the result to data/processed/. That way every correction is documented and can be redone.
  2. Everything in data/processed/ and output/ can be deleted and recreated by running the scripts. If it cannot, some step of the analysis is not in the code.
  3. Scripts are numbered in the order they run: A01_import.R, A02_clean.R, A03_model.R. Anyone joining the project knows where to start. The letter before the number is a lab convention: a script name never starts with a number, and the A01_, A02_… prefix keeps the running order in the file listing.

1.4.3 Step 3: put the data in data/raw/

Download the pilot trial file: ensaio_milho_piloto.csv (right-click and choose Save link as if the browser opens the file instead of downloading it). The file name is Portuguese for “maize pilot trial”; the data are shared by both language versions of the book.

The browser saves the file in your downloads folder, which is not part of the project. It has to go to data/raw/. You can drag it in the file manager or, better, move it from R, in the project’s console:

file.copy(
  from = "~/Downloads/ensaio_milho_piloto.csv",   # where the browser saved it
  to = "data/raw/"                                 # into the project
)
#> [1] TRUE

list.files("data/raw")
#> [1] "ensaio_milho_piloto.csv"

On Windows, the downloads folder is C:/Users/your_user/Downloads. If file.copy() returns FALSE, the file was not found at the source path: check the name and folder with list.files("~/Downloads").

1.5 File paths

1.5.1 Absolute and relative

An absolute path starts at the root of the file system and identifies the file unambiguously, but only on that machine:

/home/ana/projects/R_Course/data/raw/ensaio_milho_piloto.csv    # Linux
/Users/ana/projects/R_Course/data/raw/ensaio_milho_piloto.csv   # macOS
C:/Users/ana/projects/R_Course/data/raw/ensaio_milho_piloto.csv # Windows

A relative path describes where the file is starting from the working directory:

data/raw/ensaio_milho_piloto.csv

Inside a project, the working directory is the project root, so the relative path works on any computer.

TipAlways use the forward slash /

R accepts the forward slash / on every system, including Windows. The backslash \ has to be doubled inside strings ("C:\\Users"), because it has a special meaning there. Use / and avoid the problem altogether.

1.5.2 Building paths with file.path()

Instead of pasting text together, use file.path(), which inserts the correct separator:

file.path("data", "raw", "ensaio_milho_piloto.csv")
#> [1] "data/raw/ensaio_milho_piloto.csv"

1.5.3 The here package

One subtle problem remains. The working directory is not always the project root. When Quarto renders a report, for instance, the working directory becomes the report’s folder. If your report lives in reports/, during rendering the relative path data/raw/ensaio_milho_piloto.csv would not exist (R would look for it in reports/data/raw/).

NotePackage intent: here

Problem it solves. Building paths that always point to the same place, no matter where the code runs (console, script, Quarto document in a subfolder, server), without setwd() and without absolute paths.

Philosophy. here finds the project root by searching from the current directory up through the parent folders for files that mark a project (a .Rproj, a .git folder, a .here file, among others). The here() function returns paths starting from that root. It is deliberately tiny: it does one thing, and does it well.

Why this one and not the alternatives.

  • setwd(): ties the code to one computer; ruled out for the reasons above.
  • Plain relative paths: work in the console but break when the working directory changes (as in Quarto documents in subfolders).
  • rprojroot: the engine behind here, more flexible but more verbose. here offers the same robustness through a one-function interface.

1.5.4 Step 4: read the data from inside the project

In the maize_trial_2025 project console, load here:

library(here)
#> here() starts at /home/ana/Documents/maize_trial_2025

The message here() starts at ... shows which folder here recognised as the root. Always check that line when you open a new project.

To build the path to the data file, pass each piece as an argument:

data_path <- here("data", "raw", "ensaio_milho_piloto.csv")
file.exists(data_path)
#> [1] TRUE

Now we read the file. In lesson 5 we will meet the readr package and its advantages; for now we use read.csv(), which ships with R:

trial <- read.csv(here("data", "raw", "ensaio_milho_piloto.csv"))

head(trial)
#>   hibrido bloco produtividade_t_ha altura_planta_cm
#> 1    HB01     1               9.54              225
#> 2    HB01     2               9.93              220
#> 3    HB01     3               8.64              201
#> 4    HB02     1               9.04              213
#> 5    HB02     2               9.00              204
#> 6    HB02     3               8.86              220

This code works the same in the console, in a script in scripts/ and in a report in reports/, on any computer that has a copy of the project. That is exactly what we wanted. (This book is also a project with the same structure, which is why the results shown here are the same ones you get in yours.)

A few quick questions for our pilot trial:

1.6 Failing on purpose: “cannot open file”

The most common error for R beginners is this one:

read.csv("ensaio_milho_piloto.csv")
#> Warning in file(file, "rt"): cannot open file 'ensaio_milho_piloto.csv': No
#> such file or directory
#> Error in `file()`:
#> ! cannot open the connection

Read the message carefully. It says two things:

  • cannot open file 'ensaio_milho_piloto.csv': R could not open a file at that path.
  • No such file or directory: the reason is that, starting from the current working directory, no file with that name exists.

A diagnostic routine that solves almost every case:

# 1. Where is R looking?
getwd()
#> [1] "/home/ana/Documents/maize_trial_2025"

# 2. Is the file where I think it is?
file.exists(here("data", "raw", "ensaio_milho_piloto.csv"))
#> [1] TRUE

# 3. What is actually in the folder? (typos and extensions show up here)
list.files(here("data", "raw"))
#> [1] "ensaio_milho_piloto.csv"

The file exists and is in the right place: the problem is that read.csv("ensaio_milho_piloto.csv") looked for it at the project root, not in data/raw/.

The most frequent causes, in order:

  1. The path is relative to the wrong place (missing here() or the data/raw folder).
  2. A typo in the name or the extension (.csv vs .CSV vs .xlsx). On Linux and macOS, upper and lower case matter.
  3. The project is not open, and the working directory is the user’s home folder.
  4. The file stayed in the downloads folder and was never moved to data/raw/.

1.7 Clean sessions: never save .RData

By default, when you close RStudio it asks Save workspace image to ~/.RData?. If you answer “yes”, every object in the session is saved and silently comes back next time. That looks convenient, but it is the main source of analyses that “work on my machine”: the result depends on objects that no script creates.

The lab rule is: the code is the source of truth, not the session. Every object must be recreatable by running the scripts from start to finish in a fresh session.

Set this up once and for all:

  • In RStudio: Tools > Global Options > General, untick Restore .RData into workspace at startup and choose Never for Save workspace to .RData on exit.
  • Or from code:
usethis::use_blank_slate()

And adopt the habit: before you consider an analysis finished, restart the session (Ctrl + Shift + F10) and run the whole script. If it works, it is reproducible.

1.8 Organising a script

A lab script always has the same anatomy. Here is an example you can save as scripts/A01_explore_pilot.R in the maize_trial_2025 project (File > New File > R Script, then save it in the scripts/ folder):

# Initial exploration of the maize pilot trial ---------------------------------
# Author: Your Name
# Goal: check that the data are read correctly and compute basic summaries.

# Packages ---------------------------------------------------------------------
library(here)

# Data -------------------------------------------------------------------------
trial <- read.csv(here("data", "raw", "ensaio_milho_piloto.csv"))

# Summaries --------------------------------------------------------------------
mean(trial$produtividade_t_ha)
tapply(trial$produtividade_t_ha, trial$hibrido, mean)
  • The header says what the script does and why.
  • Packages are loaded at the top, all together. A reader immediately knows what the script depends on.
  • Lines ending in ---- create navigable sections in RStudio (Ctrl + Shift + R inserts one). Use the section menu at the bottom of the editor to jump between them.
  • There is no setwd() and no rm(list = ls()).

1.9 Under the hood

1.9.1 What is inside a .Rproj

The .Rproj file is a plain text file with the project options. Since the working directory is the project root, the file name is enough:

readLines("maize_trial_2025.Rproj")
#>  [1] "Version: 1.0"                 ""                            
#>  [3] "RestoreWorkspace: No"         "SaveWorkspace: No"           
#>  [5] "AlwaysSaveHistory: Default"   ""                            
#>  [7] "EnableCodeIndexing: Yes"      "Encoding: UTF-8"             
#>  [9] ""                             "AutoAppendNewline: Yes"      
#> [11] "StripTrailingWhitespace: Yes" "LineEndingConversion: Posix" 
#> [13] ""

RStudio uses these options (for example RestoreWorkspace: No) and creates next to it a hidden .Rproj.user/ folder with the interface state (open tabs, history). That folder is personal and never goes into Git.

1.9.2 How here finds the root

here walks up the folder tree from the working directory until it finds a project marker. The dr_here() function explains its reasoning:

here::dr_here()
#> here() starts at /home/ana/Documents/maize_trial_2025.
#> - This directory contains a file matching "[.]Rproj$" with contents matching
#>   "^Version: " in the first line
#> - Initial working directory: /home/ana/Documents/maize_trial_2025/reports
#> - Current working directory: /home/ana/Documents/maize_trial_2025/reports

In this example, dr_here() was called while rendering a report in reports/: the working directory was reports/, and here still found the root through the .Rproj. The root is determined only once, when the package is loaded. So if you switch projects, restart the session.

1.9.3 Why rm(list = ls()) is not enough

library(here)
rm(list = ls())
search()   # the "here" package is still attached to the session
#>  [1] ".GlobalEnv"        "package:here"      "package:stats"  ...

ls() only lists the objects in the global environment. Loaded packages, options and environment variables survive. The only real clean-up is restarting the session.

1.9.4 The tilde ~ and your home path

The tilde ~ is a shortcut for your home folder. path.expand() shows where it points:

path.expand("~/projects")
#> [1] "/home/ana/projects"

It is handy in the console for opening projects, but it is still a user-specific path and must not appear inside analysis scripts.

Summary

  • All R work in the lab happens inside a project (.Rproj), which sets the working directory automatically.
  • Never use setwd() or absolute paths in scripts. Use paths relative to the project root, built with here().
  • Standard structure: data/raw (read-only), data/processed, scripts, R, output, reports.
  • The cannot open file ... No such file or directory error is diagnosed with getwd(), file.exists() and list.files().
  • The code is the source of truth. Do not save .RData; restart the session and run everything again to check reproducibility.
