4  Packages and the ecosystem

Lesson goals

By the end of this lesson you will be able to:

  1. Explain what a package is and where it is stored on your computer.
  2. Install packages from CRAN, Bioconductor and GitHub.
  3. Tell installing from loading, and library() from ::, and resolve conflicts between functions with the same name.
  4. Understand what the tidyverse proposes and use the native pipe |>.
  5. Record a project’s package versions with renv, so the analysis runs the same two years from now.
  6. Judge whether an unfamiliar package deserves your trust.

4.1 What a package is

A package is an organised bundle of functions, documentation, example data and tests, distributed in a standard format. Everything we have used so far (mean(), lm(), factor()) comes from packages that ship with R, such as base and stats. The community’s thousands of packages extend R into virtually any field, quantitative genetics included: lme4, sommer, AlphaSimR, BGLR and asreml itself.

Two concepts that are often confused:

  • Repository: the online “catalogue” packages are downloaded from. The main ones are CRAN (the official repository, with over 20,000 automatically checked packages), Bioconductor (specialised in bioinformatics and genomics) and GitHub (code under development, with no formal review). r-universe is a platform that builds packages straight from GitHub, widely used by projects such as rOpenSci.
  • Library: the folder on your computer where installed packages are stored.
.libPaths()   # where this R installation's libraries live
#> [1] "/home/ana/R/x86_64-pc-linux-gnu-library/4.6"
#> [2] "/usr/lib/R/library"

There are usually two: a personal one (where the packages you install go) and a system one (with the packages that ship with R).

4.2 Installing packages

Installing means downloading the package and storing it in the library. You do it once per computer (and again when you want to update):

# From CRAN
install.packages("janitor")
install.packages(c("readxl", "lubridate"))   # several at once

# From Bioconductor (needs the BiocManager package)
install.packages("BiocManager")
BiocManager::install("SNPRelate")

# From GitHub ("user/repository" format)
install.packages("pak")
pak::pak("rstudio/gt")
NotePackage intent: pak

Problem it solves. Installing packages from different sources requires different tools (install.packages(), BiocManager, remotes), and dependency failures show up halfway through the installation, sometimes leaving the library half-updated.

Philosophy. pak offers a single function, pak::pak(), that understands packages from CRAN ("dplyr"), Bioconductor ("bioc::SNPRelate") and GitHub ("user/repo"). It resolves every dependency before installing, downloads in parallel and, on Linux, tells you which operating-system libraries are missing.

Why this one and not the alternatives. install.packages() remains perfectly valid for CRAN, and it is what you will see in most tutorials. pak wins when a project mixes sources or when installing a package with many dependencies fails in obscure ways. The remotes package, long used to install from GitHub, has in practice been superseded by pak.

WarningNever put install.packages() in an analysis script

Installing is an action on the computer, not part of the analysis. A script that reinstalls packages every time it runs is slow, may update versions without you noticing and fails without internet. Install from the console; record the versions with renv (see below).

4.2.1 ASReml-R is a special case

asreml is not on CRAN: it is commercial software from VSN International, distributed under licence. It is installed from the file VSN provides, and the licence must be activated once per machine. We will cover the details in lesson 44 and in the installation appendix.

4.3 Loading packages

Loading makes the package’s functions available in the current session. You do it in every session in which you use the package:

library(janitor)
#> 
#> Attaching package: 'janitor'
#> The following objects are masked from 'package:stats':
#> 
#>     chisq.test, fisher.test

Now janitor’s functions can be called by name:

clean_names(data.frame(`Produtividade (sc/ha)` = 62.4, check.names = FALSE))
#>   produtividade_sc_ha
#> 1                62.4

The alternative is not loading it and calling the function with the :: operator, as we already did with usethis::create_project():

janitor::make_clean_names(c("Planting Date", "Yield (kg/ha)", "Plant Height"))
#> [1] "planting_date" "yield_kg_ha"   "plant_height"
Form When to use it
library(package) at the top of the script packages used many times in the script (dplyr, ggplot2)
package::function() functions used once or twice, or when the name could be ambiguous

require() also loads packages, but it only returns FALSE (with a warning) when the package is missing, instead of stopping with an error. In analysis scripts prefer library(): if a package is missing, it is better to find out on the first line.

4.3.1 Conflicts: two functions with the same name

When two loaded packages have functions with the same name, the one from the last loaded package wins, and R warns you that it “masks” the earlier one:

library(dplyr)
#> 
#> Attaching package: 'dplyr'
#> The following objects are masked from 'package:stats':
#> 
#>     filter, lag
#> The following objects are masked from 'package:base':
#> 
#>     intersect, setdiff, setequal, union

The message says, for example, that dplyr::filter() masks stats::filter(). From now on, filter() means the dplyr version. If you need the other one, use :::

stats::filter(1:10, rep(1/3, 3))   # moving average, the time-series function

Conflicts like these cause confusing errors (“unused argument”, “object not found”) when you think you are calling one function and are calling another. The conflicted package turns any conflict into an explicit error, forcing you to choose:

library(conflicted)
conflicts_prefer(dplyr::filter)

4.3.2 Which version do I have?

packageVersion("dplyr")
#> [1] '1.2.1'
packageVersion("janitor")
#> [1] '2.2.1'

sessionInfo() shows the R version, the operating system and every loaded package. Copy its output whenever you ask for help or report a bug: it answers half the questions anyone would ask.

sessionInfo()

4.4 The tidyverse

NotePackage intent: tidyverse

Problem it solves. Base R grew over decades, with functions written by different people with different conventions: argument order varies, names mix styles (read.csv, readRDS, nchar) and each function returns a different kind of object. That slows down learning and makes code hard to read.

Philosophy. The tidyverse is a collection of packages that share a grammar:

  • the data always come first, in a table (tibble), which lets functions be chained with the pipe;
  • each function does one thing, with a verb for a name (filter, select, mutate, summarise);
  • names use snake_case, and functions in the same family start the same way (str_detect, str_replace; read_csv, read_tsv);
  • code is written to be read by people, not just executed.

Why this one and not the alternatives. For trial data analysis, the tidyverse offers the gentlest learning curve and the largest community, with extensive documentation in Portuguese and English. Base R remains essential (and we will use it whenever it is simpler), and data.table is the choice for tables with tens of millions of rows. The lab adopts the tidyverse as its standard because the code stays readable for whoever reviews it, including yourself a year from now.

library(tidyverse) loads the core packages in one go:

library(tidyverse)
#> ── Attaching core tidyverse packages ─────────────────── tidyverse 2.0.0.9000 ──
#> ✔ forcats   1.0.1     ✔ readr     2.2.0
#> ✔ ggplot2   4.0.3     ✔ stringr   1.6.0
#> ✔ lubridate 1.9.5     ✔ tibble    3.3.1
#> ✔ purrr     1.2.2     ✔ tidyr     1.3.2
#> ── Conflicts ────────────────────────────────────────── tidyverse_conflicts() ──
#> ✖ dplyr::filter() masks stats::filter()
#> ✖ dplyr::lag()    masks stats::lag()
#> ℹ Use the conflicted package (<http://conflicted.r-lib.org/>) to force all conflicts to become errors
Package Role Lesson
readr importing text files (CSV, TSV) 5
tibble modern tables 3
dplyr transforming tables: filtering, creating columns, summarising 6, 10, 11
tidyr reshaping tables: long and wide format 7
stringr working with text 8
forcats working with factors 8
lubridate working with dates 8
purrr functional programming 14, 15
ggplot2 plots Module 3

The tidyverse also includes packages that are not loaded automatically, such as readxl (Excel spreadsheets) and haven (SPSS, Stata and SAS files). They are installed along with it but loaded separately.

4.5 The pipe |>

The pipe passes the result on its left as the first argument of the function on its right. Read |> as “and then”:

yield_bags_ha <- c(62.4, 58.1, 70.3, 66.0, 65.8, NA)

# Without the pipe: we read from the inside out
round(mean(yield_bags_ha * 60 / 1000, na.rm = TRUE), digits = 2)
#> [1] 3.87

# With the pipe: we read top to bottom, in the order things happen
(yield_bags_ha * 60 / 1000) |>
  mean(na.rm = TRUE) |>
  round(digits = 2)
#> [1] 3.87

Both forms do exactly the same thing. The pipe’s advantage grows with the number of steps: in an analysis with ten transformations, the nested version becomes unreadable, and creating ten intermediate objects clutters the environment.

4.5.1 |> or %>%?

You will find two pipes in R code:

|> (native) %>% (magrittr)
Available since R 4.1 (2021) 2014, via a package
Needs a package? no magrittr (loaded by the tidyverse)
Placeholder _ (only in a named argument) . 
# When the data do not go in the first argument, use the named placeholder
cars |> lm(dist ~ speed, data = _) |> coef()
#> (Intercept)       speed 
#>  -17.579095    3.932409

The lab standard is |>. It does not depend on a package and is slightly faster. Set RStudio’s shortcut (Ctrl + Shift + M) to insert it: Tools > Global Options > Code and tick Use native pipe operator.

TipPipe style

Put each step on its own line, with |> at the end of the previous line and the next line indented by two spaces. Avoid chains of more than 8 to 10 steps; if it gets long, create an intermediate object with a name that explains what it is.

4.6 Reproducible versions with renv

Imagine you finished your dissertation analysis in 2026. In 2028, a reviewer asks for a change. In the meantime you have updated R and every package, and one function changed its behaviour: the script no longer runs, or worse, it runs and gives a different result.

NotePackage intent: renv

Problem it solves. By default, every project on your computer uses the same library. Updating a package for a new project can break an old one, and there is no record of which versions each project used.

Philosophy. renv gives each project its own library and a renv.lock file that records the exact version of every package used. Whoever clones the project runs renv::restore() and gets the same versions. The workflow has three verbs: init (activate), snapshot (record the current state) and restore (recreate the recorded state).

Why this one and not the alternatives. Containers (Docker) freeze the whole operating system and are the most complete solution, but they demand infrastructure and know-how that most analyses do not need. renv solves the part that breaks most often, package versions, without leaving R. It replaced the older packrat.

The workflow, always inside the project:

renv::init()       # once: creates the project library and renv.lock

# ... you install packages and work as usual ...
install.packages("lme4")

renv::snapshot()   # records the versions in use in renv.lock
renv::status()     # shows whether renv.lock is in sync with what the code uses

# On another computer, after cloning the project:
renv::restore()    # installs exactly the versions in renv.lock

renv.lock is a text file and goes into Git. The renv/library/ folder, which holds the packages themselves, does not: it is recreated by restore().

4.7 How to evaluate an unfamiliar package

Found a package that promises to solve your problem? Before basing a thesis on it, ask five questions:

  1. Where does it live? CRAN and Bioconductor require packages to pass automatic checks on several systems. A package that only lives on GitHub has passed none.
  2. Is it alive? When was the last release? Do the GitHub issues get answers?
  3. Who maintains it? An established research group, a company, a single person?
  4. Does it have documentation and a paper? Serious scientific packages usually have a vignette and a published paper describing the methods (like those for lme4, sommer and BGLR, which are in this book’s references).
  5. How many dependencies does it bring? Each dependency is one more thing that can break.
# How many packages does dplyr require, directly and indirectly?
deps <- tools::package_dependencies("dplyr", db = installed.packages(), recursive = TRUE)
length(deps$dplyr)
#> [1] 19

4.8 Under the hood

4.8.1 The search path

When you type a function name, R looks for it in a sequence of environments, the search path:

search()
#>  [1] ".GlobalEnv"        "package:lubridate" "package:forcats"  
#>  [4] "package:stringr"   "package:purrr"     "package:readr"    
#>  [7] "package:tidyr"     "package:tibble"    "package:ggplot2"  
#> [10] "package:tidyverse" "package:dplyr"     "package:janitor"  
#> [13] "package:stats"     "package:graphics"  "package:grDevices"
#> [16] "package:utils"     "package:datasets"  "package:methods"  
#> [19] "Autoloads"         "package:base"

The search starts in the global environment (.GlobalEnv, where your objects live) and goes through the packages in reverse order of loading. That is why the last loaded package “wins” a conflict.

4.8.2 :: loads without attaching

Using package::function() loads the package’s namespace (its code is available in memory), but does not put it on the search path:

"package:lubridate" %in% search()     # the tidyverse attached lubridate
#> [1] TRUE
"package:readxl" %in% search()        # readxl is not attached
#> [1] FALSE
invisible(readxl::excel_sheets(here::here("data", "raw", "milho_met_2024.xlsx")))
"readxl" %in% loadedNamespaces()      # but now it is loaded
#> [1] TRUE
"package:readxl" %in% search()        # and is still off the search path
#> [1] FALSE

4.8.3 Where each file of a package lives

system.file() finds files installed with a package, such as example data:

system.file("extdata", package = "readxl") |> list.files()
#>  [1] "clippy.xls"    "clippy.xlsx"   "datasets.xls"  "datasets.xlsx"
#>  [5] "deaths.xls"    "deaths.xlsx"   "geometry.xls"  "geometry.xlsx"
#>  [9] "type-me.xls"   "type-me.xlsx"

4.9 Exercises

  1. Installing and loading. Explain, in one sentence each, why these snippets are wrong in an analysis script and how to fix them:
install.packages("dplyr")
library(dplyr)
require(lme4)
model <- lmer(yield ~ (1 | hybrid), data = trial)
TipSolution

In the first, install.packages() reinstalls the package every time the script runs; installing should be done once from the console and recorded with renv::snapshot(). Only library(dplyr) stays.

In the second, if lme4 is not installed, require() returns FALSE with a warning and the error only appears on the next line (could not find function "lmer"), far from its cause. With library(lme4) the error appears on the right line.

  1. Pipe. Rewrite with the native pipe, one step per line:
round(sqrt(sum((c(2.1, 3.4, 2.8) - mean(c(2.1, 3.4, 2.8)))^2) / 2), 3)
TipSolution 
x <- c(2.1, 3.4, 2.8)

((x - mean(x))^2) |>
  sum() |>
  (\(total) total / 2)() |>
  sqrt() |>
  round(digits = 3)
#> [1] 0.651

sd(x) |> round(3)   # and, of course, there is already a function for this
#> [1] 0.651

The step (\(total) total / 2)() is an anonymous function, which we will see in detail in lesson 14. The exercise shows a limit of the pipe: when a step is not a simple function call, the piped version can look stranger than the original. With well-named intermediate objects, the calculation is clearer.

  1. Conflicts. After library(dplyr), which function does filter() call? And lag()? Use search() and environment(filter) to confirm.
TipSolution 
environment(filter)
#> <environment: namespace:dplyr>
environment(lag)
#> <environment: namespace:dplyr>

Both come from dplyr, which was attached after stats and therefore appears before it in search().

  1. Evaluation. Pick a genetics package you use or plan to use (for example sommer, AGHmatrix or rrBLUP). Answer the five questions from “How to evaluate an unfamiliar package” for it.

Start with packageDescription("sommer") (version, maintainer, date) and citation("sommer") (reference paper). The package’s CRAN page shows the results of the automatic checks, and its GitHub repository shows recent activity.

Summary

  • Repositories (CRAN, Bioconductor, GitHub, r-universe) are catalogues; the library is the local folder holding installed packages.
  • Install once, from the console; load in every session, at the top of the script. Use :: for one-off or ambiguous functions.
  • The last loaded package wins name conflicts; conflicted makes this explicit.
  • The tidyverse is a collection of packages with a shared grammar; the |> pipe chains steps in the order they happen.
  • renv records the project’s versions in renv.lock, which goes into Git; renv::restore() recreates the environment.
