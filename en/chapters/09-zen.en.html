9.1 What the “Zen of R” is

Throughout this module we have built up a set of habits. Together they make up what the Brazilian R community calls the Zen of R (O Zen do R) (Trecenti and Lente 2021): a way of organising work so that it is reproducible, readable and easy to pick up again. The principles we adopt in the lab:

  1. Everything is a project. A folder, a .Rproj, a Git repository (lesson 1).
  2. Relative paths with here(), never setwd() (lesson 1).
  3. Raw data are sacred. data/raw/ is read-only; every correction is code (lesson 5).
  4. Code is the source of truth. No .RData; any result must be recreated by running the scripts in a clean session (lesson 1).
  5. Recorded versions with renv (lesson 4).
  6. Readable code: consistent style, descriptive names, small functions (this lesson).
  7. Full history with Git (this lesson).

This lesson closes the module by making all these principles work together.

9.2 Code style

Code is read far more often than it is written, and almost always by someone else (or by you, months later, which is practically someone else). A consistent style cuts the effort of reading. The lab follows the tidyverse style guide, whose main rules you have already been practising:

Rule Yes No
Names in snake_case prod_kg_ha, read_soy_2025() ProdKgHa, read.soy()
<- to assign x <- 5 x = 5
Spaces around operators and after commas mean(x, na.rm = TRUE) mean(x,na.rm=TRUE)
One pipe step per line x |> ↵ filter() everything on one long line
Lines up to 80 characters
Two-space indentation tabs

Nobody needs to memorise spacing rules: two tools do it for you.

NotePackage intent: styler and lintr

Problem they solve. Reviewing style by hand is tedious, subjective and pulls attention away from what matters in a code review: the logic.

Philosophy. The two work together, with complementary roles. styler fixes formatting automatically (spaces, indentation, line breaks) without changing what the code does. lintr points out problems that need a human decision, such as names off the standard, long lines, unused objects or using = to assign.

Why these and not the alternatives. They are the community’s reference tools, configured by default for the tidyverse guide, integrated into RStudio (the Addins menu) and into GitHub Actions. The alternative, an IDE’s own formatter, is not standardised across editors and checks neither names nor logic.

messy_code <- "average<-function(x,drop_na=TRUE){
if(drop_na){x=x[!is.na(x)]}
sum( x )/length(x)}"

styler::style_text(messy_code)

9.3 Functions in R/, scripts in scripts/

In lesson 8, the soybean cleaning pipeline took more than 20 lines. If it were copied into every script or chapter that uses the soybean data, every fix would have to be made everywhere. The solution is to turn it into a function and keep it in R/.

The division of responsibilities in the project:

Folder Contains Runs on its own?
R/ definitions of reusable functions no: it only defines functions
scripts/ the analysis, in numbered steps yes, from start to finish
data/raw/ data as they arrived not code
data/processed/ clean data, produced by scripts/ not code
output/ tables and figures, produced by scripts/ not code

This project’s R/funcoes_dados.R file gathers the reading and cleaning steps from lessons 5 to 8. The lab’s code uses Portuguese names, since it is shared by the whole team:

# Funções de leitura e limpeza dos dados do curso ----------------------------
#
# Usadas pelos scripts em scripts/ e pelos capítulos a partir da aula 9.
# Carregue com: source(here::here("R", "funcoes_dados.R"))

#' Lê o ensaio de milho 2023/24 (Excel, uma aba por local)
#'
#' @param arquivo Caminho da planilha.
#' @return Um tibble com uma linha por parcela e a coluna `safra`.
ler_milho_2024 <- function(arquivo = here::here("data", "raw", "milho_met_2024.xlsx")) {
  readxl::excel_sheets(arquivo) |>
    rlang::set_names() |>
    purrr::map(\(aba) {
      readxl::read_excel(arquivo, sheet = aba, skip = 3, na = c("", "-", "perdida"))
    }) |>
    purrr::list_rbind(names_to = "local") |>
    janitor::clean_names() |>
    dplyr::mutate(
      safra = "2023/24",
      data_plantio = lubridate::dmy(data_plantio)
    )
}

#' Lê o ensaio de milho 2024/25 (CSV em formato largo)
#'
#' @param arquivo Caminho do CSV.
#' @param locais Tabela de locais com as colunas `local` (código) e `municipio`.
#' @return Um tibble longo, com os nomes de locais iguais aos de 2023/24.
ler_milho_2025 <- function(arquivo = here::here("data", "raw", "milho_met_2025_largo.csv"),
                           locais = ler_locais()) {
  readr::read_csv(arquivo, show_col_types = FALSE) |>
    tidyr::pivot_longer(
      cols = tidyselect::starts_with("prod_"),
      names_to = "local",
      names_prefix = "prod_",
      values_to = "prod_kg_ha"
    ) |>
    dplyr::left_join(dplyr::select(locais, local, municipio), by = "local") |>
    dplyr::mutate(local = municipio, safra = "2024/25", .keep = "unused")
}

#' Lê a tabela de locais
ler_locais <- function(arquivo = here::here("data", "raw", "locais.csv")) {
  readr::read_csv(arquivo, col_types = "ccfddi")
}

#' Lê e limpa o ensaio de soja 2025 (CSV brasileiro, latin1)
#'
#' @param arquivo Caminho do CSV.
#' @return Um tibble limpo, com cultivares padronizadas, acamamento lógico e datas.
ler_soja_2025 <- function(arquivo = here::here("data", "raw", "soja_ensaio_2025.csv")) {
  readr::read_delim(
    arquivo,
    delim = ";",
    locale = readr::locale(decimal_mark = ",", encoding = "latin1"),
    show_col_types = FALSE
  ) |>
    janitor::clean_names() |>
    dplyr::mutate(
      cultivar = cultivar |>
        stringr::str_squish() |>
        stringr::str_to_upper() |>
        stringr::str_replace(" ", "-"),
      acamamento = stringr::str_to_lower(acamamento) == "sim",
      data_semeadura = lubridate::as_date(
        lubridate::parse_date_time(data_de_semeadura, orders = c("dmy", "ymd"))
      ),
      data_maturacao = data_semeadura + lubridate::days(dias_ate_maturacao)
    ) |>
    dplyr::select(-data_de_semeadura) |>
    dplyr::relocate(data_semeadura, data_maturacao, .after = bloco)
}

Note three choices:

  • Each function starts with a comment stating what it takes and what it returns. The #' format is the one roxygen2 uses to document packages (appendix C); if these functions ever become the lab package, the documentation is already in place.
  • Every package function is called with :: (readr::read_csv(), dplyr::mutate()). A function in R/ should not depend on library() being called somewhere else: it has to work in any script.
  • Default paths use here(), but they can be swapped through an argument. That makes it possible to test the function on another file without editing it.

To use the functions, a script loads them with source():

9.4 Capstone project: from raw data to results

Module 1’s complete workflow fits into two scripts.

9.4.1 Step 1: prepare the data

scripts/A01_preparar_dados.R (prepare data) reads the four raw files, joins the two maize seasons, standardises the soybean data, checks that the data are as expected and writes the results to data/processed/:

# Prepara os dados dos ensaios de milho e soja --------------------------------
#
# Entrada: data/raw/ (somente leitura)
# Saída:   data/processed/milho_met.rds e data/processed/soja_ensaio.rds
#
# Uso: Rscript scripts/A01_preparar_dados.R

# Pacotes ---------------------------------------------------------------------
library(dplyr)
library(here)

source(here("R", "funcoes_dados.R"))

# Milho: duas safras em uma tabela ---------------------------------------------
locais <- ler_locais()

milho <- bind_rows(ler_milho_2024(), ler_milho_2025(locais = locais)) |>
  mutate(
    local = factor(local, levels = sort(unique(local))),
    hibrido = factor(hibrido),
    bloco = factor(bloco),
    safra = factor(safra)
  ) |>
  relocate(safra, .before = local)

# Soja ------------------------------------------------------------------------
soja <- ler_soja_2025() |>
  mutate(across(c(local, cultivar, bloco), factor))

# Conferências: o script para aqui se algo estiver fora do esperado -----------
stopifnot(
  "milho: 2 safras x 4 locais x 20 híbridos x 3 blocos" = nrow(milho) == 2 * 4 * 20 * 3,
  "milho: parcelas duplicadas" = anyDuplicated(select(milho, safra, local, hibrido, bloco)) == 0,
  "milho: locais sem nome" = !anyNA(milho$local),
  "soja: 2 locais x 15 cultivares x 4 blocos" = nrow(soja) == 2 * 15 * 4,
  "soja: código de cultivar fora do padrão" = all(grepl("^SJ-\\d{2}$", soja$cultivar)),
  "soja: data de semeadura faltante" = !anyNA(soja$data_semeadura)
)

# Gravação --------------------------------------------------------------------
dir.create(here("data", "processed"), showWarnings = FALSE)
readr::write_rds(milho, here("data", "processed", "milho_met.rds"))
readr::write_rds(soja, here("data", "processed", "soja_ensaio.rds"))

message("Gravados: data/processed/milho_met.rds (", nrow(milho), " linhas) e ",
        "data/processed/soja_ensaio.rds (", nrow(soja), " linhas)")

The most important part of the script is the stopifnot() with named messages. If a future season arrives with one hybrid too many, a duplicated plot or a cultivar spelled in a new way, the script stops with a clear message instead of silently producing wrong results.

9.4.2 Step 2: summarise

scripts/A02_resumir_ensaios.R (summarise trials) starts only from the processed data and produces the results tables in output/tables/:

# Resumos descritivos dos ensaios ---------------------------------------------
#
# Entrada: data/processed/milho_met.rds e data/processed/soja_ensaio.rds
#          (gerados por scripts/A01_preparar_dados.R)
# Saída:   output/tables/*.csv
#
# Uso: Rscript scripts/A02_resumir_ensaios.R

# Pacotes ---------------------------------------------------------------------
library(dplyr)
library(tidyr)
library(here)

milho <- readr::read_rds(here("data", "processed", "milho_met.rds"))
soja <- readr::read_rds(here("data", "processed", "soja_ensaio.rds"))

pasta_saida <- here("output", "tables")
dir.create(pasta_saida, recursive = TRUE, showWarnings = FALSE)

# Milho: qualidade de cada ambiente (safra x local) ---------------------------
ambientes_milho <- milho |>
  summarise(
    n_parcelas = n(),
    n_perdidas = sum(is.na(prod_kg_ha)),
    media_kg_ha = mean(prod_kg_ha, na.rm = TRUE),
    cv_pct = 100 * sd(prod_kg_ha, na.rm = TRUE) / media_kg_ha,
    .by = c(safra, local)
  ) |>
  arrange(safra, local)

# Milho: médias dos híbridos em cada ambiente, em formato largo ----------------
medias_milho <- milho |>
  summarise(media_kg_ha = mean(prod_kg_ha, na.rm = TRUE), .by = c(hibrido, safra, local)) |>
  mutate(ambiente = paste(local, safra, sep = "_")) |>
  select(hibrido, ambiente, media_kg_ha) |>
  pivot_wider(names_from = ambiente, values_from = media_kg_ha)

# Milho: ranking geral e consistência entre ambientes ---------------------------
ranking_milho <- milho |>
  summarise(media_kg_ha = mean(prod_kg_ha, na.rm = TRUE), .by = c(hibrido, safra, local)) |>
  mutate(posicao = min_rank(desc(media_kg_ha)), .by = c(safra, local)) |>
  summarise(
    media_geral_kg_ha = mean(media_kg_ha),
    vezes_no_top5 = sum(posicao <= 5),
    pior_posicao = max(posicao),
    .by = hibrido
  ) |>
  arrange(desc(media_geral_kg_ha))

# Soja: médias por cultivar e local -------------------------------------------
medias_soja <- soja |>
  summarise(
    produtividade_sc_ha = mean(produtividade_sc_ha, na.rm = TRUE),
    peso_100_sementes_g = mean(peso_100_sementes_g, na.rm = TRUE),
    dias_ate_maturacao = mean(dias_ate_maturacao),
    pct_acamamento = 100 * mean(acamamento),
    .by = c(local, cultivar)
  ) |>
  arrange(local, desc(produtividade_sc_ha))

# Gravação --------------------------------------------------------------------
readr::write_csv(ambientes_milho, file.path(pasta_saida, "milho_ambientes.csv"))
readr::write_csv(medias_milho, file.path(pasta_saida, "milho_medias_hibrido_ambiente.csv"))
readr::write_csv(ranking_milho, file.path(pasta_saida, "milho_ranking.csv"))
readr::write_csv(medias_soja, file.path(pasta_saida, "soja_medias_cultivar_local.csv"))

message("Tabelas gravadas em output/tables/")

9.4.3 Running the workflow

In a clean session, running both scripts in order recreates everything from the raw data:

source(here("scripts", "A01_preparar_dados.R"), local = new.env())
#> Gravados: data/processed/milho_met.rds (480 linhas) e data/processed/soja_ensaio.rds (120 linhas)
source(here("scripts", "A02_resumir_ensaios.R"), local = new.env())
#> Tabelas gravadas em output/tables/

local = new.env() runs each script in a separate environment, so that objects from one do not “leak” into the other: script 2 only works if everything it needs is in the files written by script 1. In the terminal, the equivalent is:

Rscript scripts/A01_preparar_dados.R
Rscript scripts/A02_resumir_ensaios.R

ImportantWhat goes into Git

data/processed/ and output/ are products of the code: they can be deleted and recreated at any time. That is why this project’s .gitignore excludes them from version control (except for a .gitkeep file that keeps the folders). What goes into Git is what cannot be recreated: raw data, code, text and renv.lock.

9.5 Git and GitHub from R

Git records the history of every file in the project: who changed what, when and why. GitHub keeps a copy of that history in the cloud and lets you collaborate, review code and publish material (like this book).

9.5.1 Initial setup (once per computer)

# Your name and e-mail will appear on every record (commit)
usethis::use_git_config(user.name = "Your Name", user.email = "your.email@university.edu")

# GitHub access token: create it in the browser and store it safely
usethis::create_github_token()
gitcreds::gitcreds_set()

# Diagnosis: checks that everything is configured
usethis::git_sitrep()

The token replaces the password when talking to GitHub. Store it through gitcreds_set(), which uses the operating system’s credential store, and never write it in a script.

9.5.2 Versioning a project

usethis::use_git()      # starts the repository and makes the first commit
usethis::use_github(private = TRUE)   # creates the repository on GitHub and pushes the code

After that, daily work happens in RStudio’s Git pane:

  1. Stage: tick the changed files that go into the record.
  2. Commit: write a short message saying what changed and why (“Fix reading of soybean sowing dates”).
  3. Push: send the commits to GitHub.
  4. Pull: bring in changes made by colleagues before you start working.
TipSmall, frequent commits

One commit per logical change (“add 2025 season reading”, “fix lower-case cultivars”) is far more useful than one giant commit at the end of the day. If something breaks, you will know exactly which change caused it and can undo it easily.

Appendix D details the lab’s collaboration workflow with branches and pull requests.

9.6 A Quarto report that reads the results

The last link in the workflow is communicating the results. A Quarto report in reports/ reads the tables in output/ (or the data in data/processed/) and never redoes the cleaning: if the data change, you just run the scripts and render the report again.

---
title: "Maize and soybean trials: descriptive summary"
author: "QGSL Lab"
date: today
format: html
execute:
  echo: false
---

```{r}
library(tidyverse)
library(here)
environments <- read_csv(here("output", "tables", "milho_ambientes.csv"))
```

## Environment quality

The maize trial lost `{r} sum(environments$n_perdidas)` plots
across `{r} nrow(environments)` environments.

```{r}
knitr::kable(environments, digits = 1)
```

The code between `{r} ...` inside the text is evaluated and replaced by its value: the report’s numbers never fall out of date with respect to the data. To render:

quarto::quarto_render("reports/trial_summary.qmd")

In lesson 17 we will see parameterised reports, which automatically generate one report per trial or per location.

9.7 Zen of R checklist

Before considering an analysis ready to share, check:

Question
☐ Does the project open through its .Rproj, with no setwd() anywhere?
☐ Is data/raw/ untouched, with every correction in code?
☐ Restarting the session and running the scripts in order, is everything recreated without errors?
☐ Do the scripts check the data (stopifnot()) before writing results?
☐ Are reusable functions in R/, calling packages with ::?
☐ Does the code pass styler, with no relevant lintr warnings?
☐ Is renv.lock up to date (renv::status())?
☐ Is everything that cannot be recreated in Git, and nothing containing passwords or tokens?

9.8 Under the hood

9.8.1 What source() does

source("file.R") reads the file and runs each expression, as if you typed them in the console. Without the local argument, the objects it creates go to the global environment, mixing with yours. With local = new.env(), they go to a new, disposable environment:

env <- new.env()
source(here("R", "funcoes_dados.R"), local = env)
ls(env)
#> [1] "ler_locais"     "ler_milho_2024" "ler_milho_2025" "ler_soja_2025"
exists("ler_milho_2024", envir = env)
#> [1] TRUE

9.8.2 What a commit is

Each commit is a complete snapshot of the project, identified by a unique code (the hash) and linked to the previous commit. The history forms a chain that can be walked backwards:

gert::git_log(max = 5)   # this project's last five commits

Because each commit stores the full state, you can always see or recover any earlier version of any file. That is why Git makes names like analysis_final_v3_fixed.R unnecessary.

Summary

  • The Zen of R gathers the module’s habits: project, here(), untouched raw data, code as the source of truth, recorded versions, consistent style and Git.
  • styler fixes formatting; lintr points out what needs a decision.
  • Reusable functions go in R/ (with :: and documentation); the analysis goes in numbered scripts/, which check the data with stopifnot() before writing.
  • data/processed/ and output/ are recreatable and stay out of Git; raw data, code and renv.lock go in.
  • Quarto reports read finished results and use inline code so the numbers never go stale.
