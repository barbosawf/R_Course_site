4  Pacotes e o ecossistema

Objetivos da aula

Ao final desta aula você será capaz de:

  1. Explicar o que é um pacote e onde ele fica guardado no seu computador.
  2. Instalar pacotes do CRAN, do Bioconductor e do GitHub.
  3. Diferenciar instalar de carregar, e library() de ::, e resolver conflitos entre funções de mesmo nome.
  4. Entender a proposta do tidyverse e usar o pipe nativo |>.
  5. Registrar as versões dos pacotes de um projeto com renv, para que a análise rode igual daqui a dois anos.
  6. Avaliar se um pacote desconhecido merece confiança.

4.1 O que é um pacote

Um pacote é um conjunto organizado de funções, documentação, dados de exemplo e testes, distribuído de forma padronizada. Tudo o que usamos até aqui (mean(), lm(), factor()) vem de pacotes que acompanham o R, como base e stats. Os milhares de pacotes da comunidade estendem o R para praticamente qualquer área, incluindo genética quantitativa: lme4, sommer, AlphaSimR, BGLR e o próprio asreml.

Dois conceitos que costumam se confundir:

  • Repositório: o “catálogo” na internet de onde os pacotes são baixados. Os principais são o CRAN (o repositório oficial, com mais de 20 mil pacotes revisados automaticamente), o Bioconductor (especializado em bioinformática e genômica) e o GitHub (código em desenvolvimento, sem revisão formal). O r-universe é uma plataforma que compila pacotes diretamente do GitHub, muito usada por projetos como o rOpenSci.
  • Biblioteca: a pasta no seu computador onde os pacotes instalados ficam guardados.
.libPaths()   # onde ficam as bibliotecas desta instalação do R
#> [1] "/home/ana/R/x86_64-pc-linux-gnu-library/4.6"
#> [2] "/usr/lib/R/library"

Normalmente há duas: uma pessoal (onde vão os pacotes que você instala) e uma do sistema (com os pacotes que vêm com o R).

4.2 Instalando pacotes

Instalar é baixar e guardar o pacote na biblioteca. Isso se faz uma vez por computador (e de novo quando você quiser atualizar):

# Do CRAN
install.packages("janitor")
install.packages(c("readxl", "lubridate"))   # vários de uma vez

# Do Bioconductor (precisa do pacote BiocManager)
install.packages("BiocManager")
BiocManager::install("SNPRelate")

# Do GitHub (formato "usuario/repositorio")
install.packages("pak")
pak::pak("rstudio/gt")
NotaIntenção do pacote: pak

Problema que resolve. Instalar pacotes de fontes diferentes exige ferramentas diferentes (install.packages(), BiocManager, remotes), e falhas de dependência aparecem no meio da instalação, às vezes deixando a biblioteca pela metade.

Filosofia. O pak oferece uma única função, pak::pak(), que entende pacotes do CRAN ("dplyr"), do Bioconductor ("bioc::SNPRelate") e do GitHub ("usuario/repo"). Ele resolve todas as dependências antes de instalar, baixa em paralelo e, no Linux, avisa quais bibliotecas do sistema operacional estão faltando.

Por que ele e não as alternativas. install.packages() continua perfeitamente válido para o CRAN, e é o que você verá na maioria dos tutoriais. O pak vence quando o projeto mistura fontes ou quando a instalação de um pacote com muitas dependências falha de forma obscura. O pacote remotes, usado por muito tempo para instalar do GitHub, foi substituído na prática pelo pak.

AvisoNunca coloque install.packages() em um script de análise

Instalar é uma ação sobre o computador, não parte da análise. Um script que reinstala pacotes toda vez que roda é lento, pode atualizar versões sem você perceber e falha sem internet. Instale pelo console; registre as versões com renv (veja abaixo).

4.2.1 O ASReml-R é um caso especial

O asreml não está no CRAN: é um software comercial da VSN International, distribuído com licença. A instalação é feita a partir do arquivo fornecido pela VSN, e a licença precisa ser ativada uma vez por máquina. Veremos os detalhes na aula 44 e no apêndice de instalação.

4.3 Carregando pacotes

Carregar é disponibilizar as funções do pacote na sessão atual. Isso se faz em toda sessão em que você usar o pacote:

library(janitor)
#> 
#> Attaching package: 'janitor'
#> The following objects are masked from 'package:stats':
#> 
#>     chisq.test, fisher.test

Agora as funções do janitor podem ser chamadas pelo nome:

clean_names(data.frame(`Produtividade (sc/ha)` = 62.4, check.names = FALSE))
#>   produtividade_sc_ha
#> 1                62.4

A alternativa é não carregar e chamar a função com o operador ::, como já fizemos com usethis::create_project():

janitor::make_clean_names(c("Data de Plantio", "Prod. (kg/ha)", "Altura Planta"))
#> [1] "data_de_plantio" "prod_kg_ha"      "altura_planta"
Forma Quando usar
library(pacote) no topo do script pacotes que você usa muitas vezes no script (dplyr, ggplot2)
pacote::funcao() funções usadas uma ou duas vezes, ou quando o nome pode ser ambíguo

require() também carrega pacotes, mas apenas devolve FALSE (com um aviso) quando o pacote não existe, em vez de parar com erro. Em scripts de análise prefira library(): se um pacote está faltando, é melhor descobrir na primeira linha.

4.3.1 Conflitos: duas funções com o mesmo nome

Quando dois pacotes carregados têm funções com o mesmo nome, vale a do último carregado, e o R avisa que ela “mascara” a anterior:

library(dplyr)
#> 
#> Attaching package: 'dplyr'
#> The following objects are masked from 'package:stats':
#> 
#>     filter, lag
#> The following objects are masked from 'package:base':
#> 
#>     intersect, setdiff, setequal, union

A mensagem diz, por exemplo, que dplyr::filter() mascara stats::filter(). Daqui em diante, filter() significa a versão do dplyr. Se você precisar da outra, use :::

stats::filter(1:10, rep(1/3, 3))   # média móvel, a função de séries temporais

Conflitos assim causam erros confusos (“argumento não usado”, “objeto não encontrado”) quando você acha que está chamando uma função e está chamando outra. O pacote conflicted transforma qualquer conflito em erro explícito, forçando você a escolher:

library(conflicted)
conflicts_prefer(dplyr::filter)

4.3.2 Qual versão eu tenho?

packageVersion("dplyr")
#> [1] '1.2.1'
packageVersion("janitor")
#> [1] '2.2.1'

sessionInfo() mostra a versão do R, o sistema operacional e todos os pacotes carregados. Copie a saída sempre que pedir ajuda ou relatar um erro: ela responde metade das perguntas que alguém faria.

sessionInfo()

4.4 O tidyverse

NotaIntenção do pacote: tidyverse

Problema que resolve. O R base cresceu ao longo de décadas, com funções escritas por pessoas diferentes e convenções diferentes: a ordem dos argumentos varia, os nomes misturam estilos (read.csv, readRDS, nchar) e cada função devolve um tipo de objeto. Isso torna o aprendizado lento e o código difícil de ler.

Filosofia. O tidyverse é uma coleção de pacotes que compartilham uma gramática:

  • os dados vêm sempre primeiro, em uma tabela (tibble), o que permite encadear funções com o pipe;
  • cada função faz uma coisa só, com nome de verbo (filter, select, mutate, summarise);
  • os nomes seguem snake_case, e funções da mesma família começam do mesmo jeito (str_detect, str_replace; read_csv, read_tsv);
  • o código é feito para ser lido por pessoas, não só executado.

Por que ele e não as alternativas. Para análise de dados de ensaios, o tidyverse oferece a curva de aprendizado mais suave e a maior comunidade, com documentação extensa em português e inglês. O R base continua essencial (e vamos usá-lo sempre que for mais simples), e o data.table é a escolha para tabelas com dezenas de milhões de linhas. O laboratório adota o tidyverse como padrão porque o código fica legível para quem vai revisá-lo, inclusive você mesmo daqui a um ano.

library(tidyverse) carrega de uma vez os pacotes principais:

library(tidyverse)
#> ── Attaching core tidyverse packages ─────────────────── tidyverse 2.0.0.9000 ──

O tidyverse inclui ainda pacotes que não são carregados automaticamente, como readxl (planilhas Excel) e haven (arquivos de SPSS, Stata e SAS). Eles são instalados junto, mas carregados à parte.

4.5 O pipe |>

O pipe passa o resultado da esquerda como primeiro argumento da função da direita. Leia |> como “e então”:

produtividade_sc_ha <- c(62.4, 58.1, 70.3, 66.0, 65.8, NA)

# Sem pipe: lemos de dentro para fora
round(mean(produtividade_sc_ha * 60 / 1000, na.rm = TRUE), digits = 2)
#> [1] 3.87

# Com pipe: lemos de cima para baixo, na ordem em que as coisas acontecem
(produtividade_sc_ha * 60 / 1000) |>
  mean(na.rm = TRUE) |>
  round(digits = 2)
#> [1] 3.87

As duas formas fazem exatamente a mesma coisa. A vantagem do pipe cresce com o número de etapas: em uma análise com dez transformações, a versão aninhada fica ilegível, e criar dez objetos intermediários polui o ambiente.

4.5.1 |> ou %>%?

Você encontrará dois pipes em código R:

|> (nativo) %>% (magrittr)
Disponível desde R 4.1 (2021) 2014, via pacote
Precisa de pacote? não magrittr (carregado pelo tidyverse)
Marcador de posição _ (só em argumento nomeado) . 
# Quando os dados não vão no primeiro argumento, use o marcador com nome
cars |> lm(dist ~ speed, data = _) |> coef()
#> (Intercept)       speed 
#>  -17.579095    3.932409

O padrão do laboratório é |>. Ele não depende de pacote e é um pouco mais rápido. Configure o atalho do RStudio (Ctrl + Shift + M) para inseri-lo: Tools > Global Options > Code e marque Use native pipe operator.

DicaEstilo com pipe

Coloque cada etapa em uma linha, com o |> no fim da linha anterior e a linha seguinte recuada em dois espaços. Evite cadeias com mais de 8 a 10 etapas; se ficar longo, crie um objeto intermediário com um nome que explique o que ele é.

4.6 Reprodutibilidade de versões com renv

Imagine que você terminou a análise da sua dissertação em 2026. Em 2028, um revisor pede uma alteração. Nesse meio-tempo, você atualizou o R e todos os pacotes, e uma função mudou de comportamento: o script não roda mais, ou pior, roda e dá outro resultado.

NotaIntenção do pacote: renv

Problema que resolve. Todos os projetos do seu computador usam, por padrão, a mesma biblioteca. Atualizar um pacote para um projeto novo pode quebrar um projeto antigo, e não há registro de quais versões cada projeto usava.

Filosofia. O renv dá a cada projeto uma biblioteca própria e um arquivo renv.lock, que registra a versão exata de cada pacote usado. Quem clona o projeto roda renv::restore() e obtém as mesmas versões. O fluxo tem três verbos: init (ativar), snapshot (registrar o estado atual) e restore (recriar o estado registrado).

Por que ele e não as alternativas. Contêineres (Docker) congelam o sistema operacional inteiro e são a solução mais completa, mas exigem infraestrutura e conhecimento que a maioria das análises não precisa. O renv resolve a parte que mais quebra, as versões dos pacotes, sem sair do R. Ele substituiu o antigo packrat.

O fluxo de trabalho, sempre dentro do projeto:

renv::init()       # uma vez: cria a biblioteca do projeto e o renv.lock

# ... você instala pacotes e trabalha normalmente ...
install.packages("lme4")

renv::snapshot()   # registra no renv.lock as versões em uso
renv::status()     # mostra se o renv.lock está em dia com o que o código usa

# Em outro computador, depois de clonar o projeto:
renv::restore()    # instala exatamente as versões do renv.lock

O renv.lock é um arquivo de texto e vai para o Git. A pasta renv/library/, que guarda os pacotes em si, não vai: ela é recriada pelo restore().

4.7 Como avaliar um pacote desconhecido

Encontrou um pacote que promete resolver seu problema? Antes de basear uma tese nele, faça cinco perguntas:

  1. Onde ele está? CRAN e Bioconductor exigem que o pacote passe por verificações automáticas em vários sistemas. Um pacote só no GitHub não passou por nenhuma.
  2. Está vivo? Quando foi a última versão? Os issues no GitHub recebem resposta?
  3. Quem mantém? Um grupo de pesquisa estabelecido, uma empresa, uma pessoa só?
  4. Tem documentação e artigo? Pacotes científicos sérios costumam ter uma vinheta e um artigo publicado descrevendo os métodos (como os do lme4, do sommer e do BGLR, que estão nas referências deste livro).
  5. Quantas dependências traz? Cada dependência é mais uma coisa que pode quebrar.
# Quantos pacotes o dplyr exige, direta e indiretamente?
deps <- tools::package_dependencies("dplyr", db = installed.packages(), recursive = TRUE)
length(deps$dplyr)
#> [1] 19

4.8 Por baixo do capô

4.8.1 O caminho de busca

Quando você digita o nome de uma função, o R a procura em uma sequência de ambientes, o caminho de busca:

search()
#>  [1] ".GlobalEnv"        "package:lubridate" "package:forcats"  
#>  [4] "package:stringr"   "package:purrr"     "package:readr"    
#>  [7] "package:tidyr"     "package:tibble"    "package:ggplot2"  
#> [10] "package:tidyverse" "package:dplyr"     "package:janitor"  
#> [13] "package:stats"     "package:graphics"  "package:grDevices"
#> [16] "package:utils"     "package:datasets"  "package:methods"  
#> [19] "Autoloads"         "package:base"

A busca começa no ambiente global (.GlobalEnv, onde ficam seus objetos) e segue pelos pacotes na ordem inversa em que foram carregados. É por isso que o último pacote carregado “vence” um conflito.

4.8.2 :: carrega sem anexar

Usar pacote::funcao() carrega o namespace do pacote (o código fica disponível na memória), mas não o coloca no caminho de busca:

"package:lubridate" %in% search()     # o tidyverse anexou o lubridate
#> [1] TRUE
"package:readxl" %in% search()        # o readxl não está anexado
#> [1] FALSE
invisible(readxl::excel_sheets(here::here("data", "raw", "milho_met_2024.xlsx")))
"readxl" %in% loadedNamespaces()      # mas agora está carregado
#> [1] TRUE
"package:readxl" %in% search()        # e continua fora do caminho de busca
#> [1] FALSE

4.8.3 Onde está cada arquivo de um pacote

system.file() encontra arquivos instalados com um pacote, como dados de exemplo:

system.file("extdata", package = "readxl") |> list.files()
#>  [1] "clippy.xls"    "clippy.xlsx"   "datasets.xls"  "datasets.xlsx"
#>  [5] "deaths.xls"    "deaths.xlsx"   "geometry.xls"  "geometry.xlsx"
#>  [9] "type-me.xls"   "type-me.xlsx"

4.9 Exercícios

  1. Instalar e carregar. Explique, em uma frase cada, por que estes trechos estão errados em um script de análise e como corrigi-los:
install.packages("dplyr")
library(dplyr)
require(lme4)
modelo <- lmer(prod ~ (1 | hibrido), data = ensaio)
DicaSolução

No primeiro, install.packages() reinstala o pacote toda vez que o script roda; a instalação deve ser feita uma vez pelo console e registrada com renv::snapshot(). Fica só o library(dplyr).

No segundo, se o lme4 não estiver instalado, require() devolve FALSE com um aviso e o erro só aparece na linha seguinte (could not find function "lmer"), longe da causa. Com library(lme4) o erro aparece na linha certa.

  1. Pipe. Reescreva com o pipe nativo, uma etapa por linha:
round(sqrt(sum((c(2.1, 3.4, 2.8) - mean(c(2.1, 3.4, 2.8)))^2) / 2), 3)
DicaSolução 
x <- c(2.1, 3.4, 2.8)

((x - mean(x))^2) |>
  sum() |>
  (\(soma) soma / 2)() |>
  sqrt() |>
  round(digits = 3)
#> [1] 0.651

sd(x) |> round(3)   # e, claro, já existe uma função para isso
#> [1] 0.651

A etapa (\(soma) soma / 2)() é uma função anônima, que veremos em detalhe na aula 14. O exercício mostra um limite do pipe: quando uma etapa não é uma chamada de função simples, a versão com pipe pode ficar mais estranha que a original. Com objetos intermediários bem nomeados, o cálculo fica mais claro.

  1. Conflitos. Depois de library(dplyr), qual função é chamada por filter()? E por lag()? Use search() e environment(filter) para confirmar.
DicaSolução 
environment(filter)
#> <environment: namespace:dplyr>
environment(lag)
#> <environment: namespace:dplyr>

Ambas vêm do dplyr, que foi anexado depois do stats e, portanto, aparece antes dele em search().

Resumo

  • Repositórios (CRAN, Bioconductor, GitHub, r-universe) são catálogos; a biblioteca é a pasta local com os pacotes instalados.
  • Instale uma vez, pelo console; carregue em toda sessão, no topo do script. Use :: para funções pontuais ou ambíguas.
  • O último pacote carregado vence os conflitos de nomes; conflicted torna isso explícito.
  • O tidyverse é uma coleção de pacotes com gramática comum; o pipe |> encadeia etapas na ordem em que acontecem.
  • renv registra as versões do projeto em renv.lock, que vai para o Git; renv::restore() recria o ambiente.
