Objetivos da aula

Ao final desta aula você será capaz de:

  1. Aplicar o guia de estilo do laboratório e verificá-lo automaticamente com styler e lintr.
  2. Separar o código de um projeto em funções (R/) e scripts numerados (scripts/).
  3. Versionar o projeto com Git e publicá-lo no GitHub a partir do R.
  4. Montar um fluxo completo e reprodutível: dados brutos → dados processados → tabelas de resultados.
  5. Escrever um relatório em Quarto que lê os resultados do projeto.

9.1 O que é o “Zen do R”

Ao longo deste módulo acumulamos um conjunto de hábitos. Juntos, eles formam o que a comunidade brasileira chama de Zen do R (Trecenti e Lente 2021): uma forma de organizar o trabalho para que ele seja reprodutível, legível e fácil de retomar. Os princípios que adotamos no laboratório:

  1. Tudo é um projeto. Uma pasta, um .Rproj, um repositório Git (aula 1).
  2. Caminhos relativos com here(), nunca setwd() (aula 1).
  3. Os dados brutos são sagrados. data/raw/ é somente leitura; toda correção é código (aula 5).
  4. O código é a fonte da verdade. Nada de .RData; qualquer resultado deve ser recriado rodando os scripts em uma sessão limpa (aula 1).
  5. Versões registradas com renv (aula 4).
  6. Código legível: estilo consistente, nomes descritivos, funções pequenas (esta aula).
  7. Histórico completo com Git (esta aula).

Esta aula fecha o módulo colocando todos esses princípios para funcionar juntos.

9.2 Estilo de código

Código é lido muito mais vezes do que é escrito, e quase sempre por outra pessoa (ou por você, meses depois, que é praticamente outra pessoa). Um estilo consistente reduz o esforço de leitura. O laboratório segue o guia de estilo do tidyverse, cujas regras principais você já vem praticando:

Regra Sim Não
Nomes em snake_case prod_kg_ha, ler_soja_2025() ProdKgHa, ler.soja()
<- para atribuir x <- 5 x = 5
Espaços ao redor de operadores e após vírgulas mean(x, na.rm = TRUE) mean(x,na.rm=TRUE)
Uma etapa do pipe por linha x |> ↵ filter() tudo em uma linha longa
Linhas de até 80 caracteres
Recuo de dois espaços tabulações

Ninguém precisa decorar regras de espaçamento: duas ferramentas fazem isso por você.

NotaIntenção dos pacotes: styler e lintr

Problema que resolvem. Revisar estilo à mão é tedioso, subjetivo e desvia a atenção do que importa numa revisão de código: a lógica.

Filosofia. Os dois trabalham em conjunto, com papéis complementares. O styler corrige automaticamente a formatação (espaços, recuos, quebras de linha) sem alterar o que o código faz. O lintr aponta problemas que exigem decisão humana, como nomes fora do padrão, linhas longas, objetos não usados ou o uso de = para atribuir.

Por que eles e não as alternativas. São as ferramentas de referência da comunidade R, configuradas por padrão para o guia do tidyverse, integradas ao RStudio (menu Addins) e ao GitHub Actions. A alternativa, um formatador da própria IDE, não é padronizada entre editores e não verifica nomes nem lógica.

9.3 Funções em R/, scripts em scripts/

Na aula 8, o pipeline de limpeza da soja ocupou mais de 20 linhas. Se ele aparecesse copiado em cada script ou capítulo que usa a soja, qualquer correção precisaria ser feita em todos os lugares. A solução é transformá-lo em uma função e guardá-la em R/.

A divisão de responsabilidades no projeto:

Pasta Contém Roda sozinho?
R/ definições de funções reutilizáveis não: só define funções
scripts/ a análise, em etapas numeradas sim, do início ao fim
data/raw/ dados como chegaram não é código
data/processed/ dados limpos, gerados por scripts/ não é código
output/ tabelas e figuras, geradas por scripts/ não é código

O arquivo R/funcoes_dados.R deste projeto reúne as leituras e limpezas das aulas 5 a 8. Veja uma das funções:

# Funções de leitura e limpeza dos dados do curso ----------------------------
#
# Usadas pelos scripts em scripts/ e pelos capítulos a partir da aula 9.
# Carregue com: source(here::here("R", "funcoes_dados.R"))

#' Lê o ensaio de milho 2023/24 (Excel, uma aba por local)
#'
#' @param arquivo Caminho da planilha.
#' @return Um tibble com uma linha por parcela e a coluna `safra`.
ler_milho_2024 <- function(arquivo = here::here("data", "raw", "milho_met_2024.xlsx")) {
  readxl::excel_sheets(arquivo) |>
    rlang::set_names() |>
    purrr::map(\(aba) {
      readxl::read_excel(arquivo, sheet = aba, skip = 3, na = c("", "-", "perdida"))
    }) |>
    purrr::list_rbind(names_to = "local") |>
    janitor::clean_names() |>
    dplyr::mutate(
      safra = "2023/24",
      data_plantio = lubridate::dmy(data_plantio)
    )
}

#' Lê o ensaio de milho 2024/25 (CSV em formato largo)
#'
#' @param arquivo Caminho do CSV.
#' @param locais Tabela de locais com as colunas `local` (código) e `municipio`.
#' @return Um tibble longo, com os nomes de locais iguais aos de 2023/24.
ler_milho_2025 <- function(arquivo = here::here("data", "raw", "milho_met_2025_largo.csv"),
                           locais = ler_locais()) {
  readr::read_csv(arquivo, show_col_types = FALSE) |>
    tidyr::pivot_longer(
      cols = tidyselect::starts_with("prod_"),
      names_to = "local",
      names_prefix = "prod_",
      values_to = "prod_kg_ha"
    ) |>
    dplyr::left_join(dplyr::select(locais, local, municipio), by = "local") |>
    dplyr::mutate(local = municipio, safra = "2024/25", .keep = "unused")
}

#' Lê a tabela de locais
ler_locais <- function(arquivo = here::here("data", "raw", "locais.csv")) {
  readr::read_csv(arquivo, col_types = "ccfddi")
}

#' Lê e limpa o ensaio de soja 2025 (CSV brasileiro, latin1)
#'
#' @param arquivo Caminho do CSV.
#' @return Um tibble limpo, com cultivares padronizadas, acamamento lógico e datas.
ler_soja_2025 <- function(arquivo = here::here("data", "raw", "soja_ensaio_2025.csv")) {
  readr::read_delim(
    arquivo,
    delim = ";",
    locale = readr::locale(decimal_mark = ",", encoding = "latin1"),
    show_col_types = FALSE
  ) |>
    janitor::clean_names() |>
    dplyr::mutate(
      cultivar = cultivar |>
        stringr::str_squish() |>
        stringr::str_to_upper() |>
        stringr::str_replace(" ", "-"),
      acamamento = stringr::str_to_lower(acamamento) == "sim",
      data_semeadura = lubridate::as_date(
        lubridate::parse_date_time(data_de_semeadura, orders = c("dmy", "ymd"))
      ),
      data_maturacao = data_semeadura + lubridate::days(dias_ate_maturacao)
    ) |>
    dplyr::select(-data_de_semeadura) |>
    dplyr::relocate(data_semeadura, data_maturacao, .after = bloco)
}

Observe três escolhas:

  • Cada função começa com um comentário dizendo o que recebe e o que devolve. O formato #' é o mesmo do roxygen2, usado para documentar pacotes (apêndice C); assim, se um dia essas funções virarem o pacote do laboratório, a documentação já estará pronta.
  • Todas as funções de pacotes são chamadas com :: (readr::read_csv(), dplyr::mutate()). Uma função em R/ não deve depender de library() chamado em outro lugar: ela precisa funcionar em qualquer script.
  • Os caminhos padrão usam here(), mas podem ser trocados por argumento. Isso permite testar a função com outro arquivo sem editá-la.

9.4 Projeto integrador: do bruto ao resultado

O fluxo completo do Módulo 1 cabe em dois scripts.

9.4.1 Etapa 1: preparar os dados

scripts/A01_preparar_dados.R lê os quatro arquivos brutos, junta as duas safras de milho, padroniza a soja, confere se os dados estão como esperado e grava os resultados em data/processed/:

# Prepara os dados dos ensaios de milho e soja --------------------------------
#
# Entrada: data/raw/ (somente leitura)
# Saída:   data/processed/milho_met.rds e data/processed/soja_ensaio.rds
#
# Uso: Rscript scripts/A01_preparar_dados.R

# Pacotes ---------------------------------------------------------------------
library(dplyr)
library(here)

source(here("R", "funcoes_dados.R"))

# Milho: duas safras em uma tabela ---------------------------------------------
locais <- ler_locais()

milho <- bind_rows(ler_milho_2024(), ler_milho_2025(locais = locais)) |>
  mutate(
    local = factor(local, levels = sort(unique(local))),
    hibrido = factor(hibrido),
    bloco = factor(bloco),
    safra = factor(safra)
  ) |>
  relocate(safra, .before = local)

# Soja ------------------------------------------------------------------------
soja <- ler_soja_2025() |>
  mutate(across(c(local, cultivar, bloco), factor))

# Conferências: o script para aqui se algo estiver fora do esperado -----------
stopifnot(
  "milho: 2 safras x 4 locais x 20 híbridos x 3 blocos" = nrow(milho) == 2 * 4 * 20 * 3,
  "milho: parcelas duplicadas" = anyDuplicated(select(milho, safra, local, hibrido, bloco)) == 0,
  "milho: locais sem nome" = !anyNA(milho$local),
  "soja: 2 locais x 15 cultivares x 4 blocos" = nrow(soja) == 2 * 15 * 4,
  "soja: código de cultivar fora do padrão" = all(grepl("^SJ-\\d{2}$", soja$cultivar)),
  "soja: data de semeadura faltante" = !anyNA(soja$data_semeadura)
)

# Gravação --------------------------------------------------------------------
dir.create(here("data", "processed"), showWarnings = FALSE)
readr::write_rds(milho, here("data", "processed", "milho_met.rds"))
readr::write_rds(soja, here("data", "processed", "soja_ensaio.rds"))

message("Gravados: data/processed/milho_met.rds (", nrow(milho), " linhas) e ",
        "data/processed/soja_ensaio.rds (", nrow(soja), " linhas)")

A parte mais importante do script é o stopifnot() com mensagens nomeadas. Se uma safra futura chegar com um híbrido a mais, uma parcela duplicada ou uma cultivar escrita de um jeito novo, o script para com uma mensagem clara, em vez de produzir resultados silenciosamente errados.

9.4.2 Etapa 2: resumir

scripts/A02_resumir_ensaios.R parte apenas dos dados processados e produz as tabelas de resultados em output/tables/:

# Resumos descritivos dos ensaios ---------------------------------------------
#
# Entrada: data/processed/milho_met.rds e data/processed/soja_ensaio.rds
#          (gerados por scripts/A01_preparar_dados.R)
# Saída:   output/tables/*.csv
#
# Uso: Rscript scripts/A02_resumir_ensaios.R

# Pacotes ---------------------------------------------------------------------
library(dplyr)
library(tidyr)
library(here)

milho <- readr::read_rds(here("data", "processed", "milho_met.rds"))
soja <- readr::read_rds(here("data", "processed", "soja_ensaio.rds"))

pasta_saida <- here("output", "tables")
dir.create(pasta_saida, recursive = TRUE, showWarnings = FALSE)

# Milho: qualidade de cada ambiente (safra x local) ---------------------------
ambientes_milho <- milho |>
  summarise(
    n_parcelas = n(),
    n_perdidas = sum(is.na(prod_kg_ha)),
    media_kg_ha = mean(prod_kg_ha, na.rm = TRUE),
    cv_pct = 100 * sd(prod_kg_ha, na.rm = TRUE) / media_kg_ha,
    .by = c(safra, local)
  ) |>
  arrange(safra, local)

# Milho: médias dos híbridos em cada ambiente, em formato largo ----------------
medias_milho <- milho |>
  summarise(media_kg_ha = mean(prod_kg_ha, na.rm = TRUE), .by = c(hibrido, safra, local)) |>
  mutate(ambiente = paste(local, safra, sep = "_")) |>
  select(hibrido, ambiente, media_kg_ha) |>
  pivot_wider(names_from = ambiente, values_from = media_kg_ha)

# Milho: ranking geral e consistência entre ambientes ---------------------------
ranking_milho <- milho |>
  summarise(media_kg_ha = mean(prod_kg_ha, na.rm = TRUE), .by = c(hibrido, safra, local)) |>
  mutate(posicao = min_rank(desc(media_kg_ha)), .by = c(safra, local)) |>
  summarise(
    media_geral_kg_ha = mean(media_kg_ha),
    vezes_no_top5 = sum(posicao <= 5),
    pior_posicao = max(posicao),
    .by = hibrido
  ) |>
  arrange(desc(media_geral_kg_ha))

# Soja: médias por cultivar e local -------------------------------------------
medias_soja <- soja |>
  summarise(
    produtividade_sc_ha = mean(produtividade_sc_ha, na.rm = TRUE),
    peso_100_sementes_g = mean(peso_100_sementes_g, na.rm = TRUE),
    dias_ate_maturacao = mean(dias_ate_maturacao),
    pct_acamamento = 100 * mean(acamamento),
    .by = c(local, cultivar)
  ) |>
  arrange(local, desc(produtividade_sc_ha))

# Gravação --------------------------------------------------------------------
readr::write_csv(ambientes_milho, file.path(pasta_saida, "milho_ambientes.csv"))
readr::write_csv(medias_milho, file.path(pasta_saida, "milho_medias_hibrido_ambiente.csv"))
readr::write_csv(ranking_milho, file.path(pasta_saida, "milho_ranking.csv"))
readr::write_csv(medias_soja, file.path(pasta_saida, "soja_medias_cultivar_local.csv"))

message("Tabelas gravadas em output/tables/")

9.4.3 Rodando o fluxo

Em uma sessão limpa, rodar os dois scripts em ordem recria tudo a partir dos dados brutos:

source(here("scripts", "A01_preparar_dados.R"), local = new.env())
#> Gravados: data/processed/milho_met.rds (480 linhas) e data/processed/soja_ensaio.rds (120 linhas)
source(here("scripts", "A02_resumir_ensaios.R"), local = new.env())
#> Tabelas gravadas em output/tables/

local = new.env() roda cada script em um ambiente separado, para que objetos de um não “vazem” para o outro: o script 2 só funciona se tudo o que ele precisa estiver nos arquivos gravados pelo script 1. No terminal, o equivalente é:

Rscript scripts/A01_preparar_dados.R
Rscript scripts/A02_resumir_ensaios.R

A tabela de ambientes mostra, para cada safra e local, o número de parcelas, as perdas, a média e o coeficiente de variação, os primeiros números que um melhorista olha para avaliar a qualidade de um ensaio. O ranking indica quais híbridos se mantiveram entre os cinco melhores nos oito ambientes.

ImportanteO que vai para o Git

data/processed/ e output/ são produtos do código: podem ser apagados e recriados a qualquer momento. Por isso, no .gitignore deste projeto, eles estão excluídos do versionamento (exceto um arquivo .gitkeep que mantém as pastas). O que vai para o Git é o que não pode ser recriado: dados brutos, código, texto e o renv.lock.

9.5 Git e GitHub a partir do R

O Git registra o histórico de cada arquivo do projeto: quem mudou, o quê, quando e por quê. O GitHub guarda uma cópia desse histórico na nuvem e permite colaborar, revisar código e publicar materiais (como este livro).

9.5.1 Configuração inicial (uma vez por computador)

# Seu nome e e-mail aparecerão em cada registro (commit)
usethis::use_git_config(user.name = "Seu Nome", user.email = "seu.email@ufv.br")

# Token de acesso ao GitHub: cria no navegador e guarda com segurança
usethis::create_github_token()
gitcreds::gitcreds_set()

# Diagnóstico: confere se está tudo configurado
usethis::git_sitrep()

O token substitui a senha nas comunicações com o GitHub. Guarde-o pelo gitcreds_set(), que usa o cofre de senhas do sistema operacional, e nunca o escreva em um script.

9.5.2 Versionando um projeto

usethis::use_git()      # inicia o repositório e faz o primeiro commit
usethis::use_github(private = TRUE)   # cria o repositório no GitHub e envia o código

Depois disso, o dia a dia acontece no painel Git do RStudio:

  1. Stage: marque os arquivos alterados que entram no registro.
  2. Commit: escreva uma mensagem curta que diga o que mudou e por quê (“Corrige leitura das datas de semeadura da soja”).
  3. Push: envie os commits para o GitHub.
  4. Pull: traga as mudanças feitas por colegas antes de começar a trabalhar.
DicaCommits pequenos e frequentes

Um commit por mudança lógica (“adiciona leitura da safra 2025”, “corrige cultivares em minúsculas”) é muito mais útil do que um commit gigante no fim do dia. Se algo quebrar, você saberá exatamente qual mudança causou o problema e poderá desfazê-la com facilidade.

O apêndice D detalha o fluxo de colaboração do laboratório com branches e pull requests.

9.7 Checklist do Zen do R

Antes de considerar uma análise pronta para ser compartilhada, confira:

Pergunta

☐ Reiniciando a sessão e rodando os scripts em ordem, tudo é recriado sem erros?

9.8 Por baixo do capô

9.8.1 O que source() faz

source("arquivo.R") lê o arquivo e executa cada expressão, como se você as digitasse no console. Sem o argumento local, os objetos criados vão para o ambiente global, misturando-se aos seus. Com local = new.env(), vão para um ambiente novo e descartável:

ambiente <- new.env()
source(here("R", "funcoes_dados.R"), local = ambiente)
ls(ambiente)
#> [1] "ler_locais"     "ler_milho_2024" "ler_milho_2025" "ler_soja_2025"
exists("ler_milho_2024", envir = ambiente)
#> [1] TRUE

9.8.2 O que é um commit

Cada commit é uma fotografia completa do projeto, identificada por um código único (o hash) e ligada ao commit anterior. O histórico forma uma cadeia que pode ser percorrida para trás:

gert::git_log(max = 5)   # os últimos cinco commits deste projeto

Como cada commit guarda o estado completo, é sempre possível ver ou recuperar qualquer versão anterior de qualquer arquivo. Por isso Git dispensa nomes como analise_final_v3_corrigida.R.

resumir_ambientes <- function(dados, variavel) {

Resumo

  • O Zen do R reúne os hábitos do módulo: projeto, here(), dados brutos intocados, código como fonte da verdade, versões registradas, estilo consistente e Git.
  • styler corrige a formatação; lintr aponta o que exige decisão.
  • Funções reutilizáveis vão em R/ (com :: e documentação); a análise vai em scripts/ numerados, que conferem os dados com stopifnot() antes de gravar.
  • data/processed/ e output/ são recriáveis e ficam fora do Git; dados brutos, código e renv.lock ficam dentro.
  • Relatórios Quarto leem os resultados prontos e usam código em linha para que os números nunca fiquem desatualizados.
